# Notas de desarrollo de Temvra (versión personal · temvra/app)

Temporizador, agenda (Día, Semana, 3 días, Mes, Año, Programación), bloques de trabajo, Notas tipo Obsidian y asistente.
Una sola base de código para **Android** (Capacitor 8, `com.temvra.app.personal`) y **escritorio** (Electron: Windows .exe y Linux AppImage).
Se prueba en un móvil Android, en un PC con Linux y en tableta.

## Dónde está cada cosa
- `src/app.html` — **toda la app** en un solo archivo (HTML + CSS + JS). El JS va dentro de una IIFE: sus funciones no son globales.
- `src/widget.html` — widget «Ahora» del escritorio y de la vista previa de Ajustes (recibe datos por `postMessage` o por `window.VTWidget`).
- `src/native.js` — puente con el plugin nativo (`window.VTNative`): temporizador en segundo plano, alarmas, widgets.
- `android/app/src/main/java/com/temvra/app/` — plugin y servicios nativos: `TimerService`, `Alerts`, `Widgets` (todos los widgets), `WidgetTick` (tic de cada minuto), `VaultDir` (bóveda en una carpeta real con el selector de carpetas del sistema).
- `desktop/` — Electron: `main.cjs`, `preload.cjs`, `preload-widget.cjs` y `vault-dir.cjs` (carpeta real de la bóveda; no usa Electron, se prueba con Node).
- `scripts/build-www.mjs` — genera `www/` (añade el `<head>` con el viewport, copia `native.js`, `widget.html` y las fuentes).
- `www/` y `android/app/src/main/assets/public/` se generan: no se editan a mano.

## Publicación
- **Cada push a `main` compila y publica una release con el APK** (`.github/workflows/android.yml`). La versión es `1.0.<run_number>` (el contador siguió igual al pasar el repositorio a la organización). Las de PC (.exe y AppImage) solo se compilan al lanzar el flujo a mano con la casilla de PC: `gh workflow run android.yml -R temvra/app --ref main -f pc=true`. No hagas push de trabajo a medias.
- Los cambios que solo tocan archivos `*.md` no lanzan compilación.
- El repositorio se llamaba `temvra/temvP`. Al cambiar el nombre de la cuenta, GitHub retiró esa dirección para siempre y la redirige a `temvra/app`: las copias antiguas de la app siguen encontrando las actualizaciones por esa redirección. No intentes recuperar el nombre `temvP` ni `temvra` para este repositorio: están retirados.
- Los enlaces de compartir antiguos (`temvra.github.io/temvP/a/#…`) los reenvía el repositorio `temvra/temvra.github.io` a `temvra.github.io/app/a/`, conservando lo que va detrás de `#`. No crees en la organización un repositorio que se llame `temvP`.
- La versión de Play se compila a mano con `play.yml` (ver `PLAY.md`), que publica también su APK en el repositorio público `temvra/descargas` (secreto `DESCARGAS_TOKEN`; el archivo siempre se llama `Temvra.apk` para que el enlace directo no cambie).
- **El repositorio es privado.** En el plan gratuito, Actions da 2.000 minutos al mes (los de Windows cuentan doble) y 500 MB para artefactos: por eso cada push compila solo el APK y `android.yml` no sube artefactos. Las páginas públicas (descarga en `temvra.github.io/app/` y compartir en `/app/a/`) están en el repositorio `temvra/temvra.github.io`, carpeta `app/`: `docs/` era la copia de aquí y deja de publicarse con el repositorio privado, así que no la edites. El actualizador de la versión personal necesita un token de solo lectura (Ajustes › Actualizaciones).
- Desde que el repositorio está en la organización, algunas subidas no lanzan la compilación. Si no aparece en Actions, lánzala a mano: `gh workflow run android.yml -R temvra/app --ref main`.
- Commits en español, con un título que diga qué cambia para el usuario.
- Antes de subir: `node scripts/check-js.mjs` sin errores, prueba en Chromium lo que hayas tocado (móvil y escritorio, sin `pageerror`) y revisa con `git status` que no haya keystores, tokens, `www/` ni archivos de prueba.
- Después, vigila la compilación hasta el final y comprueba que la release tenga el .apk (y el .exe y el .AppImage si lanzaste también las de PC):
  - `gh run watch <id> -R temvra/app --exit-status` (si falla: `gh run view <id> -R temvra/app --log-failed`)
  - `gh api repos/temvra/app/releases?per_page=1 -q '.[0] | .tag_name + " " + .html_url'`

## Reglas
- **Nunca** leas, subas ni compartas el keystore, `android/keystore.properties` ni tokens. Los secretos solo viven en los secretos del repositorio (`KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`).
- Textos de la interfaz en español; las traducciones a otros 9 idiomas van en `DICT` (`DICT.push(...)`).
- El estado vive en `S` y se guarda con `save()` en `localStorage` (`vt2_state`). Las migraciones van por `S.uiV`: súbelo si añades una.
- Animaciones: solo `transform` y `opacity` en lo que se mueve cada fotograma; escribe en el DOM solo si el valor cambia (`setTx`, `put` en las lentes). Nada de bucles `requestAnimationFrame` que sigan corriendo en reposo.
- El color del rayo de la hora sale de las variables `--lz`, `--lz2`, `--lz3`, `--lzd` (formato `R G B`): no pongas rojos fijos.
- Sincronización con GitHub: Notas usa `ghSync`; Agenda y Time usan `appSync` y guardan un JSON por elemento en `.temvra/` del repo de la bóveda. Nunca sincronices con un repositorio de código (`GH_CODE_MARK`). Toda lectura a la API va con `cache:'no-store'` (`ghApi`): GitHub responde `max-age=60` y en el PC (Electron) el navegador devolvía durante un minuto la rama de antes de la última subida; en Android no, porque `CapacitorHttp` hace las llamadas por código nativo (de ahí salía «422 · Update is not a fast forward» y que volviera la versión anterior de una nota recién subida). Si al mover la rama llega un 422 porque otro dispositivo subió a la vez, `ghSync` y `appSync` lo repiten sobre lo nuevo.
- Deshacer y rehacer en Notas (Ctrl+Z / Ctrl+Y con la lista elegida o nada escribiéndose): no se registra cada operación. `save()` avisa a `fsDirty` y `fsCheck` compara la estructura (`fsSnap`: títulos, carpetas, qué notas y adjuntos existen, `S.folders`, orden) con la anterior; si cambió, apila el antes y el después. Escribir en una nota no cuenta, ni lo que llega con `ghBusy` o `__dirBusy`. Varios pasos seguidos (soltar diez archivos) van en `fsBatch`. Las imágenes y archivos borrados se guardan un rato en memoria (`ATTX`, en `delImg` y `fileDel`) para poder devolverlos.
- Lista de Notas con el teclado: ↑ ↓, Intro, F2, Supr, Ctrl+C / X / V (las carpetas solo se mueven) y Ctrl+Mayús+N. Pegar texto, imágenes o archivos de fuera, o soltarlos desde el explorador, pasa por `obImport` (notas para .md/.txt, adjuntos para lo demás; .json/.ics/.zip como «abrir con»); lo nuevo sale resaltado (`obNew`). Soltar algo con la app en otra sección la lleva a Notas.
- Arrastrar una nota o un adjunto fuera de la ventana (solo PC): al salir el puntero, la página manda nombre y bytes por `VTDesktop.dragOut`; `main.cjs` los escribe en `temp/temvra-arrastre` y llama a `webContents.startDrag`. El soltado real en el escritorio solo se puede comprobar en una ventana de verdad.
- Ordenar arrastrando funciona con cualquier orden: `obCustom(p)` pasa ese nivel a orden propio partiendo de lo que se veía (`S.obFolderSort[p]`; `''` es lo que no está en ninguna carpeta).
- Zoom del PC: `main.cjs` (Ctrl + / − / 0 en `before-input-event`, guardado en `userData/zoom.json`) y la página para Ctrl+rueda (`VTDesktop.zoom`), salvo donde la rueda ya tiene su propio zoom (línea de tiempo, día, lienzo).
- Actualizaciones del PC: se descargan en `userData/updates` (`fetchTo`, con `.part` hasta terminar) y se instalan al cerrar la app (`will-quit`). Al arrancar, `updClean()` borra las de la versión actual o anteriores, los `.part` y lo que no lleva versión, y de las más nuevas deja solo la última. Antes no se borraba nada: en el PC del usuario sumaban 1,3 GB.
- Registros: `r.rep` decide qué días sale sola una fila: sin definir, cada día; `{w:[0-6]}` días de la semana; `{m:[1-31]}` días del mes (el 31 cae en el último día de los meses cortos); `{off:1}` solo a mano. `ensureRegs` rellena los días que tocaban desde `last` (como mucho dos meses atrás) y esas filas se quedan aunque estén vacías.
- Editor en el móvil: `autoGrow` guarda y repone el desplazamiento de `.ne-body` (al medir, el área de texto se encoge un instante); `scroll-padding-bottom` deja el cursor por encima de la barra de formato fija y `neCaret()` lo pone a la vista cuando se abre el teclado.
- Buscar en la nota: la lupa de la cabecera y Ctrl+F (`nfOpen`; sin nota abierta, Ctrl+F abre la búsqueda en todas). Sin distinguir mayúsculas ni acentos (`nfFold` guarda a qué carácter original corresponde cada uno). En lectura se envuelven los resultados en `mark.nf` dentro de `#ne-read`; editando se pintan en `#ne-fhl`, una copia transparente del texto detrás de `#ne-hl` (misma letra, por eso también lleva la clase `ne-hl`). Esc la cierra antes que el Esc general (escucha en la captura de `window`).
- Enfoque (pestaña de Tiempo, `fcRender`): sesiones con un tanto por ciento de tiempo para las apps que distraen, inicio ahora o programado, límite por hora y estadísticas en `S.focus` (`sessions`, `cur`, `apps`, `hour`). La app manda la configuración a Android con `fcPush` → `focusSet`; `Focus.java` la guarda (el bloqueo sigue con la app cerrada) y mide el uso con `UsageStatsManager` (permiso «Acceso a datos de uso»). `FocusGuard`, un servicio de accesibilidad que solo recibe qué app pasa delante, enseña `FocusBlock` cuando se acaba el tiempo y vuelve a mirar justo cuando se acabaría si la app sigue abierta. No se pulsa Inicio antes de abrir `FocusBlock`: esa orden llega tarde y la taparía. Los textos nativos llegan ya traducidos en `tx`. Los avisos de empezar y terminar van por `upcoming()`. Antes de abrir cada permiso en Ajustes sale su aviso destacado (`fcDisclose`, lo exige Google Play): uno por permiso, en su propio diálogo; solo «Aceptar» abre Ajustes y cerrarlo de cualquier otra forma es un no. `Focus.protectedPkgs` (Ajustes, instalador, permisos, Google Play, escritorio y la propia Temvra) nunca se bloquea ni se puede elegir. Al empezar una sesión programada, su aviso (`fc|s|…`) pone también la notificación fija (`Alerts.fireDue`). `focusStatus().can` mira si el manifiesto declara `FocusGuard`: la versión de Play no lleva el servicio ni el permiso mientras `src/play/AndroidManifest.xml` los quite, y entonces Enfoque no enseña el bloqueo ni la fila de «Permitir ajustes restringidos», que en Play sobra. En el PC solo hay sesiones y estadísticas. Forzar la detención de la app hace que Android quite el servicio de la lista de activados (visto en ColorOS): `S.focus.guardSeen` recuerda que estuvo activo y Enfoque avisa para volver a activarlo. Con la APK instalada fuera de una tienda, Android 13+ pide «Permitir ajustes restringidos» en la información de la app antes de activar el servicio. En el emulador se activa con `appops set <paquete> GET_USAGE_STATS allow` y `settings put secure enabled_accessibility_services <paquete>/com.temvra.app.FocusGuard`; en el móvil de pruebas, eso lo hace el usuario.
- Seguridad (revisión del 2026-11-21): todo lo que llega de fuera (compartido, bóveda .zip, GitHub) pasa por `sane()` antes de guardarse, y al arrancar también lo guardado (ids sin comillas ni etiquetas, colores CSS válidos, imágenes solo `data:image/…;base64`). Al pintar, las imágenes van con `safeSrc`, los colores con `cssColor` y los enlaces del lienzo con `safeUrl`; los textos, siempre con `esc`. `inl()` aparta cada trozo de HTML que genera (marcas `\u0001`) para que una sustitución no pueda empezar dentro de los atributos de otra. pdf.js se abre con `isEvalSupported:false` (CVE-2024-4367). Los actualizadores solo aceptan `https://api.github.com/repos/temvra/app/releases/assets/N` con el nombre de siempre: en el PC la ruta que manda la página se normaliza (`updFile`) y en Android solo se instala un APK de `cache/updates` del mismo paquete y con la misma firma (`Updater.trusted`); el token solo viaja a api.github.com. Capacitor lleva `DisableDeploy` (que nada cambie la web que se carga al arrancar). La bóveda en carpeta no lee ni escribe nada oculto (`visible` en `vault-dir.cjs` y en `VaultDir`), salvo su propia `.trash`. `npm test` prueba un contenido compartido malicioso y el actualizador del PC.
- Bóveda en una carpeta real: `dirSync` en `src/app.html` (fusión de 3 vías con `v.dir.base`, por bóveda en `v.dir`); en Android `VaultDir.java` y en el PC `vault-dir.cjs`, que solo abre carpetas elegidas en el diálogo (`carpetas.json` del perfil). Nunca se borra en la carpeta: va a su `.trash`. La carpeta y GitHub (`ghSync`) no corren a la vez (`window.__dirBusy`) y lo que llega de la carpeta se sube a GitHub como cualquier cambio.
- Cambios pequeños y comentados en español, siguiendo el estilo compacto que ya tiene el archivo.

## Android (Capacitor 8 · targetSdk 36 · JDK 21)
- Paquete Java `com.temvra.app`; id de aplicación `com.temvra.app.personal`.
- Widgets: todos se pintan en `Widgets.java` (`refreshAll` recorre cada proveedor). Un widget nuevo necesita: clase `AppWidgetProvider`, layout en `res/layout`, `res/xml/<nombre>_info.xml`, `<receiver>` en el manifest, textos en `strings.xml` y añadirlo a `refreshAll` y al recuento de `scheduleTick`.
- En RemoteViews solo valen layouts y vistas permitidas (FrameLayout, LinearLayout, TextView, ImageView, TextClock, Chronometer, ProgressBar…). No uses `View` como separador: usa un `LinearLayout` vacío.
- Los datos de los widgets llegan de JS (`VTAPI.widgetData()`) y se guardan en SharedPreferences; el tic de cada minuto (`WidgetTick`) los refresca sin abrir la app.
- `android:allowBackup="true"` devuelve datos viejos al reinstalar: tenlo en cuenta al probar.
- Tamaño de letra de los widgets: lo elige el usuario en Ajustes (`S.wFs`, llega como `fs` en `widgetData()`). Todo texto de un widget pasa por `Widgets.size(v, id, sp * k)` con `k = Widgets.fs(d)`; lo que va en una caja de alto o ancho fijo usa `fsBox(k)` y agranda la caja con `setViewLayoutHeight/Width` (Android 12+). Con `k = 1` nada debe cambiar.
- Los altos y anchos de texto se miden con `Widgets.lineDp` y `Widgets.textPaint` (la letra real del sistema), no con proporciones fijas: en ColorOS, con la fuente del usuario, el texto es más ancho de lo que mide un `Paint` nuevo.
- Sonda de widgets (solo debug, `android/app/src/debug`): `adb shell am start -S -n com.temvra.app.personal.prueba/com.temvra.app.WidgetProbe --ef fs 1.3 [--es only pulse,line] [--ei w 340 --ei h 180]` pinta los widgets dentro de la app con datos de ejemplo y escribe en logcat (`-s 'TemvraProbe:*'`) el tamaño de cada texto y los que se cortan. Úsala al tocar un layout o un cálculo de widget.
- Widgets en el inicio real: `python3 scripts/widgets-inicio.py <carpeta fuera del repo>` recorta de la pantalla de inicio solo los widgets de Temvra (con el móvil en la página donde están) y da el tamaño de cada texto. Usa la jerarquía de vistas del lanzador (`dumpsys activity`), porque `uiautomator dump` falla en el inicio de ColorOS («could not get idle state»). El lanzador de OPPO monta el widget más grande de lo que ocupa y lo encoge a ~0,6 (un hueco de 198 dp recibe 295 dp): por eso la letra se ve pequeña y existe el ajuste de tamaño.
- Línea de tiempo: la lista solo se centra en la hora actual al colocar el widget, al tocar «Ahora» y la primera vez tras instalar otra versión o reiniciar el móvil (`lineStamp`), que es cuando el lanzador la rehace desde las 00:00. En los refrescos normales no se mueve, para respetar el desplazamiento del usuario.
- Sin el SDK de Android a mano, la compilación se comprueba en GitHub Actions. Valida al menos que los XML estén bien formados y que todo recurso nuevo esté declarado (manifest, `strings.xml`, `res/xml`).

## Escritorio (Electron)
- La app se sirve desde el protocolo propio `app://temvra` (`ORIGIN`); solo esa ventana puede usar el IPC (`fromApp(e)`).
- Todo lo que la página puede pedir pasa por `preload.cjs` (`window.VTDesktop`); el widget tiene su propio `preload-widget.cjs` (`window.VTWidget`) con lo mínimo.
- Archivo nuevo en `desktop/` que deba ir en el instalador → añádelo a `build.files` de `desktop/package.json`.
- Se publica para Windows (.exe) y Linux (AppImage).

## Cómo probar
- `npm test`: sintaxis y pruebas en Electron sin ventana (`scripts/pruebas.mjs`), con perfiles temporales, en español (sea cual sea el idioma del equipo) y sin internet: perfil vacío, todas las vistas, calendario al centrar el día, aro de la burbuja, crear un bloque sin categorías y guardado cuando no cabe en localStorage. Hazlo antes de publicar.
- Sintaxis: `node scripts/check-js.mjs` después de cada cambio en `src/`, `desktop/` o `scripts/`.
- En navegador: Playwright + Chromium sirviendo `src/app.html` envuelto en
  `<!doctype html><html lang="es"><head><meta charset="utf-8"><meta name="viewport" content="width=device-width,initial-scale=1,viewport-fit=cover"></head><body>` + archivo + `</body></html>`
  (sin el viewport el móvil se ve como escritorio). Siembra el estado con `addInitScript` en `localStorage.vt2_state` (con `tourDone:1` y lo que necesites) y abre la página con `?notour`.
- Navega con clics reales: `.nav-in button[data-view="cal|time|notes"]`, `.nav-set` (Ajustes), `#cal-vseg [data-cv=…]` y `#bk-vseg [data-cv=…]` para las vistas de la agenda.
- Tamaños: móvil 412×900 (`hasTouch`), tableta 800×1280 y 1280×800 (`isMobile`), escritorio 1440×900. `DESK` = ancho ≥ 900 (o apaisado ≥ 640).
- Rendimiento: con CDP `Emulation.setCPUThrottlingRate {rate:4}` para parecerse a un móvil, mide fotogramas con `requestAnimationFrame` y `Performance.getMetrics` (`TaskDuration`) en reposo y en las transiciones. En la app hay un medidor de fps (Ajustes › Rendimiento) que copia un informe por vistas.
- Carpeta real: en el navegador define `window.__dirTestBackend` con `addInitScript` (`kind`, `pick`, `list`, `read`, `write`, `trash`, `move`, `mkdir` sobre un objeto en memoria). En Electron, escribe `carpetas.json` (array con la ruta) en el perfil temporal para permitir una carpeta sin el diálogo. Electron como root necesita `--no-sandbox`.
- Sincronización con GitHub: no uses la API real; simula `api.github.com` con un servidor git en memoria (refs, commits, trees, blobs) compartido por dos contextos del navegador. `scripts/github-falso.js` es ese servidor para `npm test` (un solo contexto): imita también la caché de un minuto del navegador y deja meter un commit ajeno en mitad de una subida (`G.alCommit`).
- Versión de pruebas que convive con la normal (`com.temvra.app.personal.prueba`, «Temvra Prueba»): `cd android && ./gradlew assemblePersonalDebug -Pprueba`.
- Android: con el móvil conectado por USB, `npm run apk` y `adb install -r android/app/build/outputs/apk/personal/debug/app-personal-debug.apk`; logs con `adb logcat | grep -i temvra`.

## Versión de Google Play
- Dos *flavors* en `android/app/build.gradle`: **personal** (`com.temvra.app.personal`, Releases de GitHub con actualizador propio) y **play** (`com.temvra.app`, para Google Play). El código es el mismo; `BuildConfig.PLAY` distingue las dos en Java y `VTBuild.channel()` en la página (`'play'` o `'personal'`).
- La de Play no lleva el actualizador (`UpdateReceiver`, `upd*` del plugin) ni los permisos `REQUEST_INSTALL_PACKAGES` y `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (`android/app/src/play/AndroidManifest.xml`). Su nombre y paquete están en `android/app/src/play/res/values/strings.xml`.
- El .aab se genera a mano en GitHub: *Actions › Compilar para Google Play › Run workflow* (`.github/workflows/play.yml`). Sale como artefacto, firmado con la clave de subida (la misma del keystore), y su número de versión es el de esa ejecución. En local: `npm run aab`.
- El push a `main` sigue compilando solo la versión personal (`assemblePersonalRelease`).
- La ficha de Play (textos, icono, gráfico destacado y capturas) está en `fastlane/metadata/android/es-ES/` y los pasos para publicar en `PLAY.md`.
- Iconos: `python3 scripts/make-icons.py` genera todos desde los SVG de `resources/` (`temvra-icono.svg` el icono completo, `icon-fg.svg` el símbolo, `icon-bg.svg` el fondo) con `rsvg-convert`: adaptativo (fondo y símbolo en PNG, el cuadrado del icono ocupa los 72 dp visibles), monocromo para los iconos temáticos, antiguo, redondo, el de las notificaciones (`ic_stat_temvra`), las `splash.png` y `resources/icon-512.png` (PC, esquinas transparentes). `icon-source.png` es el PNG original del diseño. La ficha de Play usa `images/icon.png` (512, PNG con alfa) y `featureGraphic.png`.
